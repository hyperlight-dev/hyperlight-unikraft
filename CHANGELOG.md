# Changelog

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [Prerelease] - Unreleased

### Added

- `AppSandbox::snapshot_with_scratch_mb` takes a snapshot that restores with another scratch size: boot with what unpacking the rootfs needs, then run guest function calls with what they need, less or more. The snapshot records the size (`snapshot_scratch_mb`). A size too small for the kernel makes the restore fail (restoring a snapshot that fits recovers the sandbox) and a boot from the snapshot fail. A guest function call that runs out of scratch ends with its process killed (status 137 with a single-process driver, such as python's) or the guest aborted, depending on what runs out first. A restore recovers the sandbox.

### Changed

- The host places the transport arena at a fixed address below the top of scratch, so a snapshot keeps it when restored with a different scratch size. Snapshots saved by an earlier release are refused: save them again. A native Unikraft kernel (`--kernel`, `SandboxBuilder::from_kernel`) built against an earlier `plat/hyperlight` can allocate over the arena: rebuild it against this kernel tree.

### Fixed

- The kernel allocated scratch pages the host reserves at the top of scratch. It now stops below them.
- A guest that ran out of scratch during a copy-on-write fault crashed the VM (an unexpected exit) instead of aborting.
- On x86, a page fault the kernel could not handle early in boot or in its fault handler ended the guest as if it had finished: a guest function call that hit one looked complete. The guest aborts.
- `hluk build`, and `hluk run --build`, refused a `[build] command` that would have run: a program named by a relative path (`./build.sh`) was looked for in the directory `hluk` ran in rather than the project's, where the command runs, so `hluk build -f path/to/project` from elsewhere said it was not on PATH; and a program the shell names by expanding a word (`${CC:-gcc}`, `"$GO"`, `~/bin/tool`, `%CC%`) was looked up as written. Such a program is now looked for in the project's directory, or left to the shell.
- `hluk build`, and `hluk run --build`, refused a `[build] command` that starts with a shell builtin it did not know as one: `until`, `unset`, `ulimit`, `umask` and other `sh` builtins on Unix, and `cmd`'s builtins (`call`, `copy`, `del`, `type`, …, in any case) on Windows, were looked up in PATH. They are left to the shell. A program named by a path that is not a file is no longer said to be missing from PATH, which a path is not looked up in: the message names the project's directory, where the command runs.

## [v0.20.1]

### Changed

- Snapshots saved by v0.20.0 and earlier releases are refused (the kernel changed); save them again.

### Fixed

- A file written in pieces in the guest's in-memory filesystem was copied whole for every piece, as the filesystem grew a file's buffer to exactly the new size each time: `head -c` writing 4 KiB at a time took 28 s for 25 MB and 163 s for 50 MB, and the guest answered nothing meanwhile (one `GET /` in 81 answered). The buffer now grows by half at least, so a file is copied a bounded number of times over however it is written: 0.3 s and 0.5 s, with the guest answering throughout. The room past the file's end holds no memory until the file grows into it, and a truncate gives back what it cuts off, so a nearly full filesystem fails no earlier than before. Stock Unikraft on QEMU has the same growth (`dd bs=4096`: 1.3 s for 10 MB, 13.5 s for 25 MB).
- A write to a file in the guest's in-memory filesystem at an offset so far past its end that the offset and the length together outgrew an offset (`pwrite()` near `LONG_MAX`) crashed the guest; as on Linux, the write is now cut short where an offset ends, and fails with `ENOSPC` for a file no memory holds or `EFBIG` at the end itself. A write longer than 2 GiB is cut short too, and reports what it wrote.
- `verl-hyperlight`: what `hluk` says on stderr before the solution runs (a note on the memory limit it runs under, say) is logged by the backend rather than returned as the solution's `stderr`.

## [v0.20.0]

### Added

- Under a memory limit (a pod's or a container's, or a systemd slice's), `--scratch-mb max`, or `scratch_mb = "max"` in a manifest, gives the guest what the limit leaves once `hluk` has 64 MiB for itself, with a note, so a pod that runs `hluk run` in its image names the size once, as its limit; a manifest's `max` falls back to the tested size where there is no limit, with a note, as `hluk build` does. The limit is read from the memory cgroup (v2 or v1), the tightest in sight. Every other size stands as before, with a note when the limit cannot hold it, or holds the guest but may not hold the snapshot a `--warm` run or `hluk snapshot save` will take. A snapshot records its guest's size (`snapshot_scratch_mb`), and `hluk snapshot run` says when the limit cannot hold it. Zero is refused as a size. The library has `cgroup_memory_limit_mb`, `scratch_mb_within` and `CONTAINER_SCRATCH_HEADROOM_MB`; a `SandboxBuilder` is sized as before.
- The library exports `cpio::from_tar` behind the default `cpio` feature: the pure-Rust tar-to-newc converter `hluk build` uses, so embedders can build an initrd without a host `cpio`. It writes its own `etc/hosts`, `etc/nsswitch.conf` and `etc/resolv.conf` over the tar's.
- `openai-agents-hyperlight` (`integrations/openai-agents/`): a sandbox provider for the [OpenAI Agents SDK](https://github.com/openai/openai-agents-python), built to the SDK's provider guide, that runs each shell command of a sandbox agent in a fresh micro-VM through `hluk run`, from a warm snapshot (`SandboxRunConfig(client=HyperlightSandboxClient())`). The workspace is a host directory shared into each guest at its own path, so the SDK's file operations, snapshots and resume work as for its local backend; the guest sees nothing else of the host but directory grants, and has no network unless hosts are allowed (`net_allow`). PTY sessions, exposed ports, sandbox users, manifest mounts and Git repository entries are refused. Linux only, with `hluk` v0.19.0 or later and `openai-agents` 0.24. Published to PyPI on its own version by `pypi-publish.yml`; CI tests it on Linux with each commit's `hluk` and `agent` image, in micro-VMs and through the SDK's `Runner`.

### Changed

- Snapshots saved by v0.19.1 and earlier releases are refused (the kernel changed); save them again.

### Fixed

- Memory the guest kernel allocated for itself was not given back: a deleted file's memory (a 200 MB file kept about 635 MiB), a process's signal descriptors and the ELF loader's record of every exec, and an exited thread's or process's stacks until the guest went idle (3000 commands run back to back ran a 256 MiB guest out of memory, and CPython's `test_gc` crashed it, #157). The kernel now gives them back, and when the guest runs out of memory the command that ran out fails, or is killed (exit 137), instead of the guest's kernel crashing: the kernel keeps the last 1 MiB for itself, so a program is killed once less than that is free. A program killing a child that held the guest's memory (`kill -9`) could not, and waited for it for good. Warm snapshots are about 3% larger, as the kernel's buffers are now backed when allocated.
- A write or truncate in the guest's in-memory filesystem that could not get memory failed with `EIO`, and a create, `mkdir()` or `rename()` with `ENOMEM`; they now fail with `ENOSPC`, as on a full tmpfs. A symlink made then had no target, and reading it crashed the guest.
- Releasing a reference to a file other than its last could drop it from the epoll sets watching it, and an epoll instance could be added to itself, which crashed the guest when it was closed (now `EINVAL`, as on Linux).
- Memory a program mapped with `mmap()` stayed mapped after its process ended, so a guest that ran child processes again and again (Azure CLI running Bicep) ran out of memory. The kernel now unmaps what a process mapped when it exits, is killed or execs; memory shared with `CLONE_VM` stays until the last process sharing it ends. In the `java` image, a JVM started after `System.exit()` gets the heap the first had, and restarts are no longer refused once the old JVMs' memory runs out.
- `munmap()` and `mprotect()` of a range that began in a 2 MiB block with nothing mapped yet missed pages past the block's end: they stayed mapped, with their memory, which a mapping made there later read, or kept their protection.
- `mremap()` failed with `ENOSYS`, so musl took the main thread's stack for a single page (`pthread_getattr_np()`), and .NET's `EnsureSufficientExecutionStack` failed. A mapping now shrinks, or grows into free space after it, in place; `MREMAP_MAYMOVE` resizes in place too and fails with `ENOMEM` where only a move would do, and `realloc()` then copies.
- Static programs linked against a glibc built for x86-64-v3, as Ubuntu 26.04's is, died with `SIGILL` before `main()`: the guest never turned AVX on, and that glibc uses AVX2 without checking. The kernel now enables AVX the first time a program uses it, and AVX-512 the first time one uses that, and turns them back on after restoring a snapshot taken since. Until then CPUID reports OSXSAVE clear, so programs that check for AVX properly keep to SSE: with AVX on, every VM exit costs more on nested AMD hosts (agent cold-snap ~33 → ~48 ms on GitHub's runners). Restoring a snapshot taken before turns AVX off again.

## [v0.19.1]

### Added

- A PHP RCE containment demo (`demos/php2shell`): a payload that runs as if a PHP engine flaw had handed an attacker code execution reaches host secrets, a C2 and a persistent webshell on bare metal, and is contained on every phase inside an hluk micro-VM (read-only mount, no network). Run with `just demos php2shell`.
- The `php` image, a tier 2 runtime: PHP 8.5 embedded in the guest, with SQLite (PDO and SQLite3), mbstring, DOM and the XML extensions, OpenSSL, sodium, zlib, bcmath, sockets and Phar, in a 23 MB rootfs that runs in 128 MiB. Code and `.php` files run in one PHP request kept for the guest's life, so what a call declares is there for the next; an uncaught exception, a fatal error or `exit()` ends the call with the status the CLI would exit with (255 for the errors), and the next call finds the engine as it was, except after a fatal error, which ends the request as it ends a script: the next call starts a new one. Guest function calls name a PHP callable (`greet`, `Handlers::greet`), JSON in and out; host function calls are `Hyperlight\call($name, ...$args)`. PHP's `memory_limit` is two thirds of the memory free at boot, and PHP 8.5's hard limit three quarters, so a script reaches them before the guest runs out, and `mt_rand()` and the other functions on PHP's default generator draw from a new seed every call, unless code gave `mt_srand()` one, and OpenSSL's gets new entropy, so a warm snapshot's clones draw their own numbers. With the `php` template and examples.
- CI runs in three tiers, described in [`docs/ci.md`](docs/ci.md): Linux and Windows on x86_64 on every pull request, macOS and Windows arm64 on pull requests labelled `ci/arm64`, and Linux arm64 too nightly, blocking nothing. A pull request runs the tier-1 jobs its files call for: documentation alone gets the spell check, `integrations/<name>/` alone gets lint, the Rust tests and that integration, smolagents bringing MCP's (the `ci/integrations` label adds them all). `ci-report.yml` re-runs a failed run on `main` once, the nightly run or the newest push's, and files each job that fails again, a timeout included, as an issue labelled `ci/nightly` or `ci/main`.
- Dependabot also proposes updates for the Rust toolchain (`rust-toolchain.toml`, labelled `ci/arm64`) and for the libraries of the Python integrations (smolagents, MCP, verl), whose caps it widens when a release past one is out (a minor, for a 0.x cap), keeping the floors CI tests.
- A driver can ask how many times the guest was restored from a snapshot (`HLCALL_IOC_RESTORES`, `hl_driver_restored()` in `drivers/hl_driver.h`), to reseed what its runtime seeded before the snapshot ([`docs/driver.md`](docs/driver.md)).

### Changed

- Snapshots saved by v0.19.0 and earlier releases are refused (the kernel changed); save them again.
- CI: pull requests labelled `ci/arm64` no longer run on the Linux arm64 runner, which `ci-passed` no longer waits for, and pushes to `main` no longer run the arm64 tests, only refresh the arm64 guest images' cache: the nightly run tests both. `ci-passed` counts only the pull request's own arm64 run, not one started by hand. Dependabot no longer labels the actions' updates `ci/arm64`.

### Fixed

- `just conformance` now and then ran a module its skip list names (`known_failures.toml`, `CONFORMANCE_SKIP`), failing the job when it crashed (`test_regrtest` on Linux arm64): the skip-list check, a pipe into `grep -q`, could read an early exit of `grep` as a miss.
- A snapshot could leave out part of a guest's memory: the kernel mapped each aligned 2 MiB of an `mmap`ed range (an ELF segment the elfloader maps, say) with one large page, which Hyperlight's snapshot drops, so a guest restored from it could fault there. The kernel now maps 4 KiB pages only, and `mmap(MAP_HUGETLB)` fails with `ENOMEM`, as on Linux without a hugepage pool.
- The drivers set every host environment variable again at the top of every call, with `setenv()`, which on musl frees the string the variable had: code still holding it read freed memory (PHP's `putenv()` keeps the string it replaces, SQLite caches `getenv("TMPDIR")`). A variable is now set only when it changed, with `putenv()` and a string that stays.
- Programs did not get random `AT_RANDOM` bytes of their own: the elfloader pointed the auxiliary vector at a stale stack frame. Go's runtime seeds from those bytes, so `math/rand` drew the same numbers in every clone of a snapshot. The bytes are now copied onto the program's stack, as Linux does.
- A program started with an empty argument or environment string (`sh -c 'cmd' ''`, a BusyBox hush pipeline led by a builtin, as `set | grep`) crashed the guest's kernel (`Assertion failure: len`). Empty strings now reach the program, as on Linux.
- Generators a runtime seeded before a snapshot kept their state in every guest restored from it, though the kernel reseeds its own: Python's `random` and NumPy's legacy `np.random`, OpenSSL (`cryptography`'s copy too), SQLite's `random()`, node's and Java's `Math.random`, Java's `ThreadLocalRandom`, DRBGs and new generators' seeds, .NET's `Random.Shared`, and bash's `$RANDOM`. The kernel now counts restores (`HLCALL_IOC_RESTORES`), and each driver reseeds them from the kernel on the first call after one; [`docs/random.md`](docs/random.md) lists what each image covers and what no driver can, such as a generator the code made before the snapshot. The bash image's BusyBox seeds `$RANDOM` when `RANDOM` is assigned, as bash does, and from the kernel rather than the pid and the clock.

## [v0.19.0]

### Added

- `verl-hyperlight` (`integrations/verl/`): runs the test cases of [verl](https://github.com/verl-project/verl)'s code rewards in micro-VMs on the training node, through `hluk run`, with `reward.sandbox_fusion.url=hyperlight://` (or `hyperlight://<image>`, or `hyperlight:///path/to/rootfs.cpio`), instead of in the grader's own process or on a Sandbox Fusion service. Each case runs from a warm snapshot, with no network or view of the host, as `python solution.py` would under Sandbox Fusion, and comes back as Sandbox Fusion's reply, so verl scores it as the service's: on 200 APPS problems its scores match Sandbox Fusion's on 199 (on the agent image all 200), at about its speed. It registers as one of verl's plugins (`verl.plugins`), which registers it as the `hyperlight` sandbox runner of a verl with sandbox runners, and routes `hyperlight://` URLs to it in an earlier one. Linux only, with `hluk` v0.19.0 or later. Published to PyPI on its own version by `pypi-publish.yml`; CI tests it on Linux with each commit's `hluk` and python image, at its floor of `filelock` and the newest.
- `smolagents-hyperlight` (`integrations/smolagents/`): a [smolagents](https://github.com/huggingface/smolagents) code executor that runs a `CodeAgent`'s code in a micro-VM through `hluk run`, published to PyPI on its own version by `pypi-publish.yml`. The guest reads each step from its console and answers on it, so it needs no network, and has none unless hosts are allowed (`net_allow`); between steps its micro-VM is paused. It registers under the `smolagents.executors` entry points, so a smolagents that loads executors from them (huggingface/smolagents#2724, not in a release yet) takes `executor_type="hyperlight"`. CI tests it with each commit's `hluk` and `agent` image, in micro-VMs on Linux and Windows, against the oldest smolagents it allows on the oldest Python, and the newest.
- `mcp-server-hyperlight` (`integrations/mcp/`): an [MCP](https://modelcontextprotocol.io) server, on stdio, whose `run_python` tool runs Python in a micro-VM that keeps its variables between calls, and whose `reset_sandbox` tool replaces it with a fresh one from the warm snapshot. It runs its guest through `smolagents-hyperlight`'s executor, so the two share the guest protocol and its bounds; the guest starts as the client starts the server, and has no network unless hosts are allowed (`--net-allow`). Published to PyPI on its own version, by `pypi-publish.yml`, which now takes the package to publish. CI tests it beside the smolagents executor, in micro-VMs on Linux and Windows: on the oldest Python with mcp, smolagents-hyperlight and smolagents at the floors it allows, from PyPI, and on the newest with the commit's smolagents-hyperlight. Each release is listed in the MCP Registry as `io.github.hyperlight-dev/mcp-server-hyperlight`, and gets a GitHub release with the Claude Desktop Extension that `integrations/mcp/mcpb/` packs; the server finds `hluk` in the install scripts' directory too, for a client that starts it without that directory on `PATH`; `--timeout` takes decimals, and `--net-allow` a list separated by commas, which the extension's settings pass; its README configures Claude Code, Claude Desktop, VS Code, Codex and the OpenAI Agents SDK.
- `clickhouse-hyperlight` (`integrations/clickhouse/`): a driver for ClickHouse's driver-based executable UDFs (ClickHouse 26.6 and later), so that `CREATE FUNCTION ... ENGINE = HyperlightPython AS '<body>'` defines a function in Python, which ClickHouse runs in micro-VMs. `CREATE FUNCTION` boots a guest from the python image, defines the function in it, and saves the guest's snapshot in the function's directory; a body that does not compile fails it with Python's error. The `executable_pool` UDF it hands ClickHouse restores that snapshot before each block, in about 1.5 ms, so nothing a block leaves in the guest reaches the next. Blocks come in RowBinary, and cross into the guest as JSON through host function calls, in pieces, so a block is not bound by what one guest function call carries; `Bool`, integers up to 64 bits, floats, `String`, and `Nullable` and `Array` of them are supported. CI tests it with each commit's kernel and python image, against a pinned ClickHouse release.
- CI builds, lints and unit-tests on Windows arm64 (hosted `windows-11-arm`), so the aarch64-pc-windows-msvc code paths (WHP on arm64) compile and pass clippy on every PR. `arm64.yml` (on `main`, and on pull requests labelled `ci/arm64`) boots the guests there too, on hyperlight's arm64 runners: Linux, macOS and Windows each run what CI runs on x86, every test suite, the demos, the smolagents, mcp and verl integrations, the CPython conformance suite and the benchmarks, with a history per host (`dev/bench/<os>-arm64`) and ceilings in `benchmarks/limits.json`, and on Linux the ClickHouse UDF tests and a guest booted by the static `hluk`. The Linux runner, a small VM under nested virtualization, runs the agent, Java, node, .NET JIT and PowerShell suites and the agent benchmark nightly instead of on every change.
- Releases and dev builds carry a Windows arm64 `hluk` (`aarch64-pc-windows-msvc`), which `install.ps1` installs on an arm64 host.
- `Mount::backend`: a guest mount served by the embedder's `FsBackend` instead of a host directory. hostfs hands it each operation the guest's VFS makes (stat, read, write, mkdir, remove, truncate, list, rename, and links and chmod, which it refuses and ignores by default), and its `io::Error`s reach the guest as errno (a panic as `EIO`), so an embedder can account for every byte written (`EDQUOT`) or keep files anywhere, while the guest's programs use them as on any mount. A read-only backend mount is asked only to read. The directory mounts are served by the same code, and behave as before (docs/fs.md).
- `NetworkPolicy::Filter`: the embedder's `NetworkFilter` decides what the guest may reach, asked for each DNS question by name and for each connect and `sendto` by address and port, with the names DNS gave the guest that address. It is asked every time, so rules the embedder changes while the guest runs apply at the next connect, with no re-boot; loopback and the metadata addresses stay refused, and the resolvers an allow list exempts take questions, as under `AllowList` (docs/net.md).
- A guest function call (a script, `--exec` code, a `--call` input) carries up to 1 MiB, from about 72 KB: the host-to-guest pool is 32 buffers of 32 KiB. A larger one fails before it is sent, with `Error::CallTooLarge`, where it failed in the transport (`H2G capacity cannot provide N buffers`); `GUEST_CALL_MAX` and `CALL_PAYLOAD_MAX` give the limits.
- `os.utime` and the like set a mounted file's times on the host (`fs_set_times`), from 1970 on (an earlier one fails with `EINVAL`); they did nothing. An `FsBackend` gets them through `set_times`, ignored by default, and gives a file's times with `FileStat::times`.

### Changed

- `NetworkPolicy` is `#[non_exhaustive]`, and has a new variant, `Filter`: a `match` on it needs a wildcard arm.
- `Mount` has a private field, the backend: make one with `Mount::rw`, `Mount::ro` or `Mount::backend` rather than a struct literal, and match it with `..` when destructuring. A backend mount's `host_path` is empty.
- Snapshots saved by v0.18.0 and earlier releases are refused (the kernels changed, the snapshot contract is 7, and on arm64 the initrd's guest address moved); save them again. Rebuild images `just build-rootfs` made on an earlier tree: their drivers predate this release's console and exec changes.
- The guest's console is a terminal only where its output reaches one: `isatty` on standard input and output is true when the host's stdin and stdout are terminals, on standard error when the host's stderr is, in both cases only while the output is echoed, and in a library embedder only once `AppSandbox::console_terminal(true)` (or `SandboxBuilder::console_terminal`) allows it, which `hluk run` does for the workload. Off a terminal, terminal requests fail with `ENOTTY` and input is not echoed. It was always a terminal. The Python driver and the C drivers' stdio keep standard output line-buffered either way. An image whose driver comes from an earlier build (a custom image built `FROM` an earlier base image) does not, and can lose Python output a call does not flush: rebuild it on this release's base image.
- A mounted file's mode is the host's (on Windows, from the read-only flag as before), where every file read `755` (`555` without write permission): `access(X_OK)` now fails on one without an execute bit, so the exec driver refuses it (`Permission denied`, status 126) and `shutil.which` and the like skip it, though `execve` (and so a shell's PATH search) still runs it. A guest's `chmod` never sets set-user-ID or set-group-ID on a host file.
- The kernel's messages stay out of the guest's output: they are Hyperlight's guest log (`GuestLogData` messages), which the host logs through `tracing` as target `hyperlight_guest`, with the library, source file and line as fields, at the levels it asks for (`SandboxBuilder::guest_log_level`; unset, a fresh guest takes Hyperlight's default, from `RUST_LOG`, else errors, and a restored one its snapshot's). They were on the guest's standard error, where a failed `execve` (a shell's PATH search, `subprocess.run` of a missing program) added four `ERR:` lines to the program's own. `hluk --log-level <level>` shows them, and without it the CLI still prints the latest when hluk itself fails or an entry point writes nothing, so one that cannot start says why, but not for a program's own failure. A crash report is still on standard error. The exec driver says why it cannot run a program (`hl: cannot execute <path>: <reason>`). The driver no longer prints `hl_driver: dispatch callback failed` after a call that exited with a status of its own, only when the driver itself fails.
- The `bash-repl` template prints its prompt only when its input is a terminal.

### Fixed

- Concurrent first runs of one guest (a pool of workers on a fresh cache, say) failed: each saved its warm snapshot into the same `<slot>.part` directory, removing the others' half-written one (`atomic write: failed to create tmp`), and removed the slot before moving its own in, under runs restoring from it. Each run now writes its own part and moves it in only when the slot is empty, or held a snapshot that would not load; parts a killed run left behind go after an hour. 16 concurrent first runs all succeed, leaving one snapshot.
- The python image had no `/etc/passwd` or `/etc/group`, so `getpass.getuser()` raised `KeyError`, and `pwd` lookups, and `~` with no `HOME`, failed. It ships the base image's.
- `link()` crashed the guest kernel on its error paths (vfscore's dentry refcount assertion): linking a directory, into a missing directory, or across file systems (from `/tmp` to `/dev`). It fails with `EPERM`, `ENOENT` and `EXDEV`, as on Linux.
- Every hluk upgrade left the warm snapshots of each guest in the cache for good: a snapshot another hluk build saved, which this one refuses, was pruned only once its rootfs was rebuilt. `hluk run` now removes those of the same rootfs when it saves its own.
- CI's benchmark jobs, x86 and arm64, failed when another job's load on a shared runner put one run over a ceiling in `benchmarks/limits.json`. They now measure such a timing again, and fail only if the second run is over too.
- A guest given a network policy and no listen ports could bind any port: `hluk run --net` with no `--port`, a manifest with `[run.net]` and no `ports`, or `SandboxBuilder::network` without `listen_ports` let the guest serve, where `--port`'s help and [net.md](docs/net.md) promise a guest that cannot. `bind()` is refused with `EACCES` now unless the port is listed, whether the guest means to listen on it or to connect from it (`source_address`); an ephemeral bind, port 0, is always allowed, so the guest can still serve on a port the host picks. A guest that serves on a port of its own needs `--port`, as the documentation said, and an embedder that served under `network` alone adds `listen_ports`; the CPython conformance recipes pass `--port all`, since those tests bind as they please and the test host is the boundary.
- `os.chmod` (and every `chmod`) on a mount failed with `EIO`: the host took the mode as unsigned and the kernel sends it signed, so the host call was refused before it ran. It now reaches the host file, permission bits only: a guest cannot set setuid, setgid or sticky.
- DNS messages are read only as far as a resolver could be asked: a name longer than 253 characters, a label with a dot or a byte that is not printable ASCII, or an extended label type makes the message no well-formed query (refused) or answer (ignored). The label `a.b` read as the two labels `a` and `b`, and a forged answer could spell out a name kilobytes long through a compression loop.
- A `sendto` on a connected TCP socket was judged by the address it named, though the data goes to the socket's peer: a guest connected to a resolver on port 53 could send anything there by naming an address the policy allows, past the check of its DNS questions. A `sendto` on a stream socket is a `send` to its peer now, checked as one.
- A guest under a block list could reach the host's loopback services through the unspecified address: a connect to `0.0.0.0` or `::` goes to loopback on Linux, and only `127.0.0.0/8` and `::1` were refused. The lists and a filter refuse the unspecified address too.
- No guest booted on Windows arm64 (#166): hyperlight-host puts WHP's emulated interrupt controller at guest physical addresses just below 4 GiB, and the initrd, mapped at `0xFEF0_0000`, ran into them past its first 17 MiB. The arm64 initrd is mapped at 4 GiB now; x86 keeps its address.
- arm64 guests under nested Hyper-V (Windows arm64 runners) crashed at random, or read zeros where they had just written: the kernel mapped the pages it allocates at run time (heap, `mmap`, file pages) Non-shareable, which the CPU does not keep coherent across processors. They are Inner Shareable now, as the boot mappings were.
- An `mmap()` hint inside the initrd was honoured, though the files extracted from it share its memory: the new mapping replaced their pages, and on x86 the kernel crashed writing it. The kernel reserves the initrd now, and the hint goes elsewhere; on arm64, whose initrd moved to 4 GiB, that is the first address HotSpot asks for.
- Python output a call left in `sys.stdout` or `sys.stderr` (or the original `sys.__stdout__` and `sys.__stderr__`) reaches the host when the call ends: text with no newline (`print(x, end='')`, `json.dump(obj, sys.stdout)`), bytes written through `sys.stdout.buffer`, and what was written before an exception, now ahead of its traceback, or a `SystemExit`. The driver flushed only the C streams under them, so this arrived with a later call's output, or never if the sandbox ended or was restored first, for runs and guest function calls alike, in the python, python-shell and agent images; output left buffered at boot no longer waits in the warm snapshot for the first call.
- An arm64 guest was killed when it touched an `mmap()` larger than the address space, which the kernel accepted: its check of a virtual address passed every address. CPython's `test_decimal`, which expects `MemoryError` from such a request, crashed the guest. The `mmap()` fails with `ENOMEM` now, as on x86.
- `stat` on a mounted file read the epoch for every time.
- `mkdir` and `rmdir` of a path with trailing slashes (`mkdir("a/b/")`, as BusyBox's `mkdir -p` passes it) failed with `ENOENT`; the working directory at a mount's root ended in `/`; a mount given with a trailing slash (`--mount=/h:/g/`) was not reached at all; `umount2` returned a positive error number.
- Input piped to a guest was echoed into its output, and a chunk of it ending in `\r` was read as ending in `\n`.

### Changed

- A guest's standard error is a stream of its own, through a new host function, `HostWriteErr`: `hluk run` writes it to its own stderr instead of its stdout, and `AppSandbox::drain_stderr` returns it apart from standard output. `drain_output` still returns both, in the order written, and drops what `drain_stderr` has not taken, so take standard error first. The kernel's own messages go to standard error too, out of the program's standard output, and so does the report of `hluk run --profile`, which shares stderr with them. A host of your own that does not register `HostWriteErr` gets standard error through `HostWrite`.
- Guest output keeps its newlines: `drain_output`, `drain_stderr` and `hluk run` no longer have a `\r` before each `\n`.
- The images the builds run are pinned by digest, as the CI actions are by commit: the base images of the drivers, the kernel builder, the examples, demos and `hluk init` templates, the images `just build-test-bins` runs, the urunc image's BuildKit frontend and the BuildKit image CI builds the kernel with (#126).
- Dependabot opens grouped version updates once a month (see `.github/dependabot.yml`) for the crates, the CI actions and the Dockerfiles' base images, digest refreshes and patch releases only for those (#135). Dependabot labels its version updates `ci/arm64`. On a pull request with that label, `ci-passed` (the required check) waits for the arm64 run and fails unless it passes, so merges, auto-merge included, wait for the arm64 tests. A label added after `ci-passed` starts counts once that job is re-run.
- The Linux release binaries are static, built with musl (`hluk-v<version>-x86_64-unknown-linux-musl.tar.gz` and `aarch64-unknown-linux-musl`), so they run on any distribution. The glibc builds of earlier releases need the glibc of the runner that built them, 2.39, which Debian 12 and Ubuntu 22.04 do not have (#141). `install.sh` installs the static one and, for a release before this, the glibc one.
- Hyperlight's virtqueue transport (hyperlight v0.18): the kernel and the host talk over two VIRTIO packed rings in scratch memory instead of the PEB's I/O stacks. Host function calls are a request and its reply in one G2H chain; guest function calls arrive in buffers the kernel posts on H2G, and their results go back on G2H. Byte vectors travel after the FlatBuffer rather than inside it. The pools are sized for 64 KiB host-call payloads, rounded up to whole pages: one host call now carries 69,620 bytes, and a guest function call 73,716. hostfs reads and writes move 64 KiB per host call instead of 32 KiB: against v0.17, reading a 64 MiB file from Python is about 55% faster and writing one about 50% (KVM). `hyperlight-host` and `hyperlight-common` move to 0.18.
- Snapshots saved by an earlier release or build are refused (the kernel, the host functions and the host transport changed); save them again. A native Unikraft kernel (`--kernel`, `SandboxBuilder::from_kernel`) built against an earlier `plat/hyperlight` no longer boots: rebuild it against this kernel tree.
- Rust 1.99 builds the project (`rust-toolchain.toml`). The arm64 `wasmtime` image is a static PIE now, as on x86_64: the driver and nothing else, without the glibc it carried (#129).
- `--port` (a manifest's `[run.net] ports`) no longer needs `--net`: on its own the guest serves TCP on the port and can open no connection of its own, as under an allow list that lists nothing (a UDP service's replies are outbound sends, so it still needs a policy); with a project, it replaces only the project's ports, not what the project may reach. In the library, `SandboxBuilder::listen_ports` without `network` does the same, where it used to leave the guest with no networking at all.

### Fixed

- `hluk run`, `hluk snapshot` and `hluk bench` kept everything a guest printed in memory until they exited, though they never read it: a long-running guest that kept printing grew the host process without end. They keep none of it now; the output still reaches the terminal.
- A path below a host mount's root longer than 1,023 bytes was cut short, and the syscall made on what was left: `mkdir` reported success and created a directory with a truncated name. It now fails with `ENAMETOOLONG`.
- A path on a host mount that was not UTF-8 (`os.stat(b'/mnt/data/\xff')`) failed the guest function call that used it, since the host takes paths as strings: the kernel now refuses it, and the syscall fails with `EILSEQ`.
- Console output written in one piece longer than 4 KiB (a long line, say) reached the host cut to its first 4 KiB, with nothing to say so; and output that was not UTF-8, or a write that ended inside a character (`cat` of a large UTF-8 file can do it), failed the guest function call that printed it. The kernel now sends console output as bytes, in as many host calls as it takes, through new `HostWrite` and `HostWriteErr` host functions, and the host decodes them, a character split between writes included, with invalid bytes as U+FFFD, for stdout and `drain_output()` alike. Stdin, the other way, had the same flaw: a character cut at a 4 KiB read, or bytes that were not UTF-8, reached the guest as U+FFFD. `ReadStdin` now hands over bytes too (the guest's terminal layer still treats them as a terminal does: it echoes them, and reads Ctrl-D as end of input).
- `hluk init NAME --template go` wrote a `go.mod` that Go refused when the name was `go`, `toolchain` or a standard-library package such as `fmt`: the module path is now `example.com/NAME`.
- A condition variable broadcast, or several signals, woke one waiter and left the others asleep in programs linked with musl, which most images use (node, dotnet-jit, java, quickjs, bash, and programs built on Alpine): the kernel refused `FUTEX_REQUEUE`, which musl's condition variables use to hand each woken waiter's successor to the mutex. It showed as rare, timing-dependent hangs, such as Java's `HttpClient` stalling on its first request on Windows hosts. `FUTEX_CMP_REQUEUE` also woke a waiter when asked to wake none, looped when requeuing onto the same futex, and crashed the kernel when a requeued waiter timed out. All four are generic Unikraft fixes, each reproduced and verified on QEMU/KVM.
- Standard error reached the host as standard output: the kernel opened fd 2 as a copy of fd 1. It is a stream of its own now (see Changed).
- Every newline a guest printed reached the host as CR-LF (`\r\n`), from a workaround for serial consoles that need a carriage return. The host gets the bytes the program wrote (see Changed).
- A command that failed to execute (a mistyped command in the bash image, `subprocess.run(['/missing'])` in python-shell) crashed the guest the next time the parent waited: the vfork child freed its parent's stack on its way out, as if it were its own. A subprocess started from a thread other than the main one failed with `ENOMEM`, for want of an allocator for the new program's stack. Both are generic Unikraft fixes, verified on QEMU/KVM.
- Kernel messages carried NUL bytes, and one longer than 191 bytes carried bytes past its buffer; it is cut there now, at a whole character, and keeps its line end. nolibc's `printf` past 1 KiB also read past its buffer; it is cut at 1 KiB.
- A pipe, a `$(...)` substitution or a redirect of an external command crashed the guest in the bash image on x86_64, and so did one in Python's `subprocess.run(..., shell=True)` in the python-shell image: a vfork child returned to userland on the kernel's TLS rather than its parent's, and musl, reading its thread pointer in the system calls the child made before `execve` (`open`, `dup2`, `close`), read kernel memory as its own; so did Python's `subprocess` once any thread had run, when libc starts taking its locks. The child now runs on its parent's TLS until `execve`, as it runs on its parent's stack; arm64 had the same code and gets the same fix.
- The `agent` image got 256 MiB when booted by path (`--initrd`, or a project built `FROM` it) rather than the 1536 MiB it is tested with, too little to unpack it into, and the guest crashed during boot. hluk sizes a guest by the runtime marker an image carries, `etc/hluk-runtime`, which no image wrote, and then by its driver, which `agent` shares with `python-shell`. The `agent` image now writes the marker, and images built from it inherit it.
- A warm snapshot kept the environment of the run that saved it: `hluk run --runtime agent --env PYTHONPATH=/x` left `/x` on `sys.path` for every later run of that snapshot. The guest saved as the warm snapshot now boots with the project's `[run] env` only, which is part of the snapshot's key, and a run's `--env` reaches its runtime driver after the save, as it does a restored one. An image with no driver, whose program reads its environment once as it starts, or a run with a `warm_exec`, which runs before the save, boots with all of it, and its snapshot is keyed by it (the newest four are kept per image). A variable a runtime reads only as it starts (`NODE_OPTIONS`, say) therefore belongs in the project's `[run] env`, or needs `--cold`.
- `PYTHONPATH` given to a restored Python guest (`hluk snapshot run --env PYTHONPATH=...`, `set_env_vars`) was in `os.environ` but not on `sys.path`, which Python reads once at startup. The `python`, `python-shell` and `agent` drivers now put its entries where startup would have, in place of the previous call's, before each call, and a variable the host stops sending goes back to the guest's own value, or away if it had none.
- Waiting for and stopping processes: `wait()` for a child that was still running slept for good (the guest deadlocked) unless it waited for any child, and with two threads waiting for two children one could sleep on; a parent paused in `sigsuspend()` for a child's SIGCHLD slept for good, so a shell's `sleep 1 & wait` hung the guest, a later `pause()` or `sigsuspend()` could return at once, for a signal already handled, and `sigsuspend()` put the caller's mask back before the signal it waited for was delivered, so its handler never ran and `while (!got) sigsuspend(&old)` never ended; a killed process lived on until its threads next left a system call, so a timeout's kill waited out a `sleep` and never ended a `cat` reading a pipe (a killed process's blocked calls are now interrupted and unwind, releasing the files they hold), and a process ended while one of its threads lent its stack to a `vfork` child (a thread running `subprocess` while another called `os._exit`) freed that stack under the child, and a thread blocked in `vfork()` resumed on that stack while its child still ran on it whenever another thread or child it had made exited or exec'd (the guest crashed); an exec'd program kept the signal handlers its parent had set, so a signal it did not catch ran its parent's code; and there was one process group and one session, so `setsid()` (Python's `start_new_session`) failed, and `killpg()` and `kill(0, ...)` signalled every process in the guest, the caller's supervisor and init included. Each process now has a group and a session as on Linux, `kill` and `wait4`/`waitid` take groups, a signal that ends a process ends it when it is sent, `execve` resets caught signals, init is spared the signals it does not handle, and waiting on a group a child leaves gives ECHILD rather than a hang.
- `pause()` returned at once on arm64 hosts, where libcs make it as `ppoll(NULL, 0, NULL, NULL)`, which the kernel refused: Python's `signal.pause()` never slept, and a program paused for a child's signal ran on. A `poll()`, `ppoll()`, `select()` or `pselect6()` with no fd to watch and no timeout now waits for a signal, as on Linux (`select(0, NULL, NULL, NULL, NULL)` hung on both architectures), and `poll(NULL, 0, ms)` sleeps instead of failing. A generic Unikraft fix, verified on QEMU/KVM.
- `execve` of a file that does not exist failed with EINVAL, not ENOENT, so Python raised `OSError` instead of `FileNotFoundError` for a missing program; `kill()` of a pid past the process table (`os.kill(99999, 0)`) crashed the kernel, and so did `pthread_kill(thread, 0)`, the check whether a thread exists; a signal sent to one thread was also marked pending on the process, so the same signal sent to the process later was dropped; a standard signal sent while one was pending leaked memory; a process with 32 signals queued could not be killed (SIGKILL and SIGTERM were refused with the rest), and crashed the kernel when one of its children exited, since the exit signal could not be queued; a signal to a process group stopped at the first member that refused it; and a SIGCHLD left at its default stayed queued, so a handler installed later ran for children long reaped, while one installed with `SA_NOCLDWAIT` never ran.
- A program that ran the guest out of memory crashed the kernel with a fault; it is now killed as Linux's OOM killer would (`Out of memory: killed process N`), and the guest exits with 137 when it was the last. A child process out of memory with others still running is killed too, but the guest still crashes freeing its memory.
- `select()` and `poll()` called a socket readable that was not: a new listener, a listener whose last connection had been accepted, and a connection whose data had been read. The `accept()` or `recv()` that followed blocked, and a `socketserver` loop never got back to its `shutdown()`.

- **Projects.** `hluk init` starts a project from a template: it writes a `hluk.toml` manifest and starter files, and pulls the published rootfs the template runs on from GHCR into a local cache (`~/.cache/hluk`; `HLUK_CACHE_DIR` overrides), pinned to the tag of this `hluk` release (`<runtime>:initrd-v<version>`) so a project keeps running under the `hluk` that made it. `hluk run` with no `--initrd` runs the project the manifest describes, its flags standing in for the manifest's keys where given; `hluk build` runs its `[build]` command and builds its `[rootfs] dockerfile` with Docker into `.hluk/rootfs.cpio`; `hluk pull` refreshes the rootfs image; `hluk templates` lists the templates; `hluk cache` lists and removes what was pulled and snapshotted. With no arguments `init` asks for the template and the name. The pull speaks the registry API itself (anonymous token, manifest, one digest-checked layer), so a project runs on any host `hluk` runs on with no Docker. See `docs/manifest.md`.
- `hluk run --runtime <name|image>` runs a published runtime image by name (`python`, `node`, `agent`, …) or full reference with no project and no local build: pulled into the cache when missing, warm by default. `hluk snapshot save --runtime` saves one the same way, and its `--warm-exec CODE` runs code before the snapshot is taken.
- `--log-level info` timings are printed to a tenth of a millisecond.
- Thirteen templates, one per runtime, compiled into the binary: `python`, `agent`, `node`, `bash`, `dotnet` (C# compiled in the guest by Roslyn), `powershell`, `go`, `rust`, `c`, `dotnet-aot` (compiled on the host with a `[build]` command and mounted into the guest), and `http-python`, `http-node`, `http-dotnet` (a Flask, Express or Kestrel server on a rootfs the project's Dockerfile extends with pip, npm or the .NET SDK, `FROM` the published `<runtime>:v<version>` base).
- **Warm starts.** A manifest with `warm = true` (every template's default), `hluk run --warm`, or `hluk run --runtime` has the first run snapshot the booted guest before the workload runs, and every later run restore it instead of booting; `--cold` boots fresh. Snapshots live in the cache, one per distinct guest and shared by every project that runs it; a rebuilt rootfs replaces the snapshots of its old file. `warm_exec` is code the runtime driver runs once before that snapshot, so what it loads is in it (`http-python` sets `import flask`, `http-node` `require('express')`). The snapshot is stamped with the rootfs file, `scratch_mb`, `entry`, `warm_exec` and the build's snapshot key, and is taken again when any of them changes; mounts, network policy and environment are supplied on restore and need no new snapshot.
- `install.sh`: `curl -fsSL https://raw.githubusercontent.com/hyperlight-dev/hyperlight-unikraft/main/install.sh | sh` installs the latest release's Linux binary into `~/.local/bin` with no Rust toolchain (`HLUK_VERSION`, `HLUK_INSTALL_DIR`), verifying it against a `SHA256SUMS` when the release has one.
- `hluk init --image-version X.Y.Z` (or `HLUK_IMAGE_VERSION`) pins another release's images than this build's, for a build between releases.
- A program the exec driver runs from a mount is checked to be position-independent before the boot (`hluk build` after its command, `hluk run` before booting), and refused with the build flag that makes it one, instead of the guest's "Image format not recognized".
- `hluk build` converts a Docker image's filesystem to the initrd CPIO in Rust (`docker export` streamed through a tar-to-newc converter that lays entries out as `find . | cpio -o -H newc` does and restores the `/etc/hosts`, `/etc/nsswitch.conf` and `/etc/resolv.conf` that `docker export` empties), so the host needs Docker and nothing else, on Windows and macOS too.

## [v0.14.1]

### Added

- `--port all` lets the guest bind any port and `--port LOW-HIGH` a range, next to single ports; the library gains `ListenPorts::all()` and `ListenPorts::with_range`. `all` is for a container runtime, whose network namespace already scopes what the guest exposes, the way `docker run -P` publishes every port.
- `hluk --version`.
- `--resolv-conf FILE` installs a resolver configuration as the guest's `/etc/resolv.conf`, at boot and again on a restore, so a snapshot resolves names where it now runs rather than where it was taken; the library has `SandboxBuilder::resolv_conf`. Without it the rootfs's own file stands, and `options single-request` is added unless present. Under an allow list, the file's nameservers are exempt on port 53 like the host's own. Kernel: the new `GetResolvConf` host function is read once the rootfs is mounted and on `resume`.

### Changed

- A restored guest gets the mounts the restore names: on `resume` the kernel fetches the host's mount table (the new `GetMounts` host function) and makes its own match, mounting what is new, unmounting what is gone and remounting an entry whose index or read-only flag changed. A warm snapshot saved without mounts serves any mount set, so an embedder restores it to run a script over host directories, and `hluk snapshot run --mount` mounts what it is given. `hluk bench` takes `--mount`, and the new `mount` workload measures a mounted restore. A mount kept busy by a file open across the snapshot stays until a restore finds it free, its operations failing with `ESTALE` meanwhile; a mount table is at most 32 mounts and 3.5 KiB of entries (`MOUNTS_MAX`, `FSTAB_ENTRIES_MAX`).
- A snapshot is named by its release and a *snapshot key*, `<release>-k<kernel>-c<contract>`: the embedded kernel's hash and a host contract number, the two things a snapshot depends on. A load matches the key, so a release that changes neither keeps every saved snapshot; one that does refuses them with `Error::SnapshotRelease`, which names the release that saved the snapshot and says to save it again, in `hluk snapshot run`, `hluk bench` and the library alike. `hluk snapshot key` prints this build's key; `SNAPSHOT_KEY` is the library's. Snapshots from 0.14.0, named by release alone, are refused the same way.
- The `net_*` host functions exist on every path, refusing every `socket()` with `EACCES` when there is no network policy (before, they were absent and a guest without a policy got `EIO`). So a snapshot saved under a policy restores without one, its sockets dying on resume, and a snapshot saved without a policy restores under one; before, the first failed the restore for the missing host functions.
- The urunc demo image (`demos/urunc`, published as `hello-urunc`) bakes its workload at `/app/hello.py` and declares it as the image's `CMD`, so `docker run` needs no command after the image name and the driver's fallback entrypoint stays out of the image contract. Its greeting now names Hyperlight.

### Fixed

- `connect(2)` with `AF_UNSPEC` dissolves a datagram socket's association, as on Linux, instead of failing. glibc's `getaddrinfo` relies on it to probe every candidate of a dual-stack answer through one IPv6 socket, so a passive lookup -- `socket.getaddrinfo(None, port, AF_UNSPEC, SOCK_STREAM, 0, AI_PASSIVE)`, what Python's `http.server` does to bind -- no longer aborts the guest with a glibc assertion on the source address. Kernel: `hostsock` forwards it as the new `net_disconnect` host function.
- A script, `--exec` or `--guest-exec` on a rootfs with no runtime driver is an error that names `--entry`, instead of a guest that exits with status 0 having run nothing.

## [v0.14.0]

### Added

- **Cooperative step model** for long-running guests. The kernel hands the vCPU back to the host when the guest goes idle, reporting when its next timer is due, instead of spinning in the VM; the host waits on that timer and on the guest's sockets, then re-enters. A guest with nothing left to wake it is reported deadlocked instead of hung forever, and a guest can be snapshotted at any boundary -- even mid-call -- and resumed later, in the same process or from disk. Library: `SandboxBuilder::boot` returns an `AppSandbox`; `run` dispatches a call and waits, `submit` dispatches without waiting, `step` advances the guest one boundary, `join` drives an entry-point workload to exit, and `snapshot` / `from_snapshot` (or `restore` in place) checkpoint and resume it, sockets included. `Yield` says why a step returned.
- A plain Linux binary can be the guest's entry point (`--entry "/bin/server --flag"`) with no runtime driver; `hluk run` drives it until it exits, and the library exposes it as `AppSandbox::join`. This is how a container runtime or an actor host runs a server in the guest.
- `asyncio` now works in the Python guest, whose event loop needs the Unix-domain sockets the kernel now enables (`examples/python/asyncio_demo.py`).
- The host learns how a call and the guest ended: a failed call carries a status (`Yield::CallFailed { status }` -- the program's own exit code, 1 for an uncaught exception, -1 when the driver could not run it), and a process exit carries the guest's status (`Yield::Exited { status }`, returned by `join`; `hluk run` exits with it). A guest that halts without reporting is an error, not an exit of unknown status.
- A restored guest is re-seeded and reconnected: the kernel reseeds its CSPRNG on restore (two clones no longer draw the same `os.urandom`, UUIDs or TLS nonces) and re-establishes its sockets (listeners rebind; connections whose peers died read as closed), so a checkpointed server keeps serving after a restore with nothing saved beside the snapshot.
- Runtime drivers receive calls through `/dev/hlcall`, each on its own thread. The device's `HLCALL_IOC_MAXLEN` ioctl reports the largest call the host can send, and `HLCALL_IOC_GETENV` hands a driver the host's current environment to refresh before each call.
- `AppSandbox::snapshot_to(dir)`, `SandboxBuilder::from_snapshot_dir(dir)` and `AppSandbox::restore_from(dir)` move a snapshot through disk. It is named by the crate version inside the directory; a load by another version fails and names the versions present.
- New docs: `docs/execution.md` (the step model and sandbox lifecycle), `docs/driver.md` (the `/dev/hlcall` driver contract and how to write a driver), `docs/clock.md` and `docs/random.md` (where the guest's clocks and random bytes come from, and what a restore does to them).

### Changed

- Network-policy hostnames are enforced at the DNS question and the destination. Under an allow list, only listed names may be looked up and only listed, resolved-at-build, or DNS-learned addresses may be reached -- the host no longer resolves names for the guest, so an address it was never given is refused. Under a block list, a blocked name is refused and re-checked at each connect (250 ms deadline; refused if the lookup fails or runs late). Malformed or non-query traffic to port 53 is refused, and the allow list's DNS exemption is UDP-only. Before, a name was enforced only through addresses the host re-resolved at every connect, so a blocked name that moved was reachable until the resolver caught up, and an allow-listed guest could query any name.
- `hluk run` and `hluk snapshot run` exit with the guest's status when the guest is what failed: `sys.exit(3)` is exit code 3 with nothing added, as running the script directly would be. A malformed `--env` (no `=`) or `--mount` (no `:`) is now an error instead of being silently ignored, and `snapshot run` drives a restored entry-point guest to its exit like `run`.
- The crate has its own error type, `hyperlight_unikraft::Error`, and every public function returns `hyperlight_unikraft::Result`, with a variant per condition (`CallFailed`, `GuestExited`, `Deadlocked`, `NoDriver`, `CallInFlight`, and so on) plus `Hyperlight` for the hypervisor layer, so an embedder matches a failed call or a deadlock instead of parsing text. `set_env_vars`, which cannot fail, no longer returns a `Result`.
- A program the guest runs no longer inherits a driver's call device or pipes (both are close-on-exec).
- The .NET JIT driver sets the GC hard limit as a share of the guest's memory (`DOTNET_GCHeapHardLimitPercent`) instead of a fixed 768 MB that never engaged, so an allocation the guest cannot serve is now a catchable `OutOfMemoryException` instead of a SIGSEGV.
- `SandboxBuilder::boot` returns an `AppSandbox` instead of a `(MultiUseSandbox, GuestConfig)` tuple; `GuestConfig` is no longer public and the free `run` is now `AppSandbox::run`. `run` fails if the guest exits before the call returns, `join` refuses a driver image with no call in flight, and `boot` refuses `kernel`/`initrd`/`entry`/`scratch_mb` on a `from_snapshot` builder or a mount path the kernel's `vfs.fstab` cannot carry (whitespace, `:`, brackets, or a relative path), instead of ignoring them.
- **Breaking, guest side**: the driver protocol changed (see Removed), so rootfs images built for 0.13.0 must be rebuilt with `just build-rootfs`.
- Kernel: guest sockets are more robust -- a `recv`/`send` on a connection whose peer died or whose host socket is gone (after a restore, or a reset while parked) returns instead of hanging, a `select`/`accept` loop no longer livelocks, and a server polling more than 64 sockets no longer stops waking.
- Kernel: transfer buffers are sized from the host's I/O stacks instead of hard-coded literals, so a socket send carries the full 64 KiB, a directory listing or symlink target is no longer cut at 8 KiB / 1 KiB, and an environment over 4 KiB no longer vanishes.
- Kernel: the periodic CSPRNG reseed timer is off, so an idle guest no longer wakes the host every 300 s, and a guest with nothing to wake it is reported deadlocked instead of waited on forever. The CSPRNG is still seeded at boot and on every restore.
- `AppSandbox::set_env_vars` no longer rejects keys starting with `HL_`; the kernel reserves no keys now.
- `AllowList::from_hosts` and `BlockList::from_hosts` fail with a `ResolveError` (naming the entry and the resolver error) instead of a `String`; several host-side policy internals are no longer public.

### Removed

- The `net_resolve` host function (unused; it ran a blocking, unfiltered resolver lookup on the vCPU thread).
- The `host_nanosleep` host function (unused; it stalled the embedder's thread up to 30 s). `net_poll` now refuses a non-zero timeout: waiting is the host's job between entries.
- The callback-and-halt driver protocol: drivers no longer write a callback pointer and halt the VM themselves, and the `HL_*` dispatch and env addresses are gone from the guest environment. `HLCALL_IOC_GETENV` replaces the raw env-refresh function pointer, and `hl_driver_init` no longer takes `envp`.
- `SNAPSHOT_TAG` and the `OciTag` re-export: embedders no longer name snapshots themselves.

### Fixed

- Interactive programs no longer echo every character twice: the serial terminal now honors the `ECHO` flag and stores the `termios` a program sets, so a shell (`hluk run --entry /bin/sh`) can turn echo off, while a program that leaves `ECHO` on still has its input echoed once.
- The Python drivers set `PATH=/usr/local/bin:/usr/bin:/bin` at startup, so `subprocess.run(["python3", ...])` and other bare-name lookups find the interpreter (a host `--env PATH` still overrides it).
- AWS's IPv6 instance-metadata address (`fd00:ec2::254`) is refused under every network policy, like the link-local metadata addresses already were.
- Snapshotting a guest whose process had already exited produced an unresumable image; `AppSandbox::snapshot` (and `snapshot_to`, `hluk snapshot save`) now refuses with `Error::GuestExited`.
- Listing a mounted directory too large for one host call (about 3,000 entries) poisoned the sandbox; the host now refuses that one listing with `EOVERFLOW` and the guest goes on. Other listing errors now reach the guest with the right errno instead of `EIO`.
- The driver FunctionCall reader (`hl_fc.h`) bounds-checks every offset, so a malformed call fails instead of reading out of bounds.
- Kernel: signal-handling fixes (`sigaltstack`) for a runtime that manages its own alternate signal stacks, so the .NET workers no longer crash the kernel when the guest runs out of memory.
- The exec driver (C, C++, Rust, Go, .NET AOT) and the PowerShell driver report the program's exit status: a non-zero exit, a signal, a C++ `std::terminate` or `exit 3` now fails the call. Before, they took the closed exit pipe for success whatever the program did.
- Kernel: a program that returns from `main()` while another of its threads sleeps no longer hangs the guest.
- The Node driver reads the next call asynchronously, so its event loop keeps turning: an `unref()`ed timer or handle left behind makes progress between calls, and the child no longer exits (and deadlocks the next call) after leaving only unref'd work.
- Kernel: a guest kernel crash now ends the call with a `GuestAborted` error and the crash dump in the output, instead of the vCPU running on and the guest spinning at 100% CPU.
- An exit inside a call ends that call with its status and leaves the runtime ready for the next, in every runtime: Python catches `SystemExit`; Node turns `process.exit()`, `process.exitCode` and uncaught errors into the status and stops the timers, servers and sockets the call left; the .NET JIT and bash drivers take a child's exit status and respawn for the next call. `sys.exit(0)` / `process.exit(0)` succeed; a non-zero code fails the call. Before, an exit could take down the whole guest or deadlock the next call.
- The Python drivers release the interpreter lock while parked between calls, so a thread or server a call left behind makes progress between calls instead of starving and waking the guest every 5 ms.
- A host environment value with a quote, backslash, newline or shell syntax no longer breaks or alters the call: the Python drivers set `os.environ` through the C API, and the bash, Node and .NET drivers quote values as literals of their language. The 4 KiB cap that silently dropped variables is gone.
- A `connect()` to a peer that never answers no longer freezes the vCPU for the OS's roughly two-minute SYN timeout: the host returns `EINPROGRESS`, the guest parks on writability, and a guest-side timeout (`socket.settimeout`) is honored.
- The network policy read an IPv4-mapped IPv6 address (`::ffff:169.254.169.254`) as an unrelated address, so a dual-stack socket could bypass the loopback, link-local and `BlockList` rules. Addresses are now checked in their IPv4 form.
- Data arriving on a socket no guest thread was reading made the host spin a full core per idle guest; the host now watches a socket for readability only while the guest is parked on it.
- The guest clock no longer runs 12% fast: the kernel asks the host for the TSC frequency (`GetTscHz`) instead of assuming 2.5 GHz.
- A guest restored from a snapshot reports the current time: the kernel re-anchors its wall clock on the host's during restore.
- `SandboxBuilder::env` variables now reach a program that is the guest's entry point, not only driver-served calls.
- Kernel: `clock_nanosleep` is implemented for the monotonic and realtime clocks (relative and `TIMER_ABSTIME`), so CPython's `time.sleep()` no longer returns immediately.
- A dispatched call is no longer capped at 16 KiB ("FunctionCall too large"); the call buffer is sized from the host's I/O buffer.

## [v0.13.0]

0.13.0 is a ground-up rewrite of the project since 0.12.1: a single `hluk` CLI plus a library, a typed guest-to-host boundary, one reproducible embedded Unikraft kernel, and a formal runtime support-tier policy. It is **not** CLI- or API-compatible with 0.12.x; see **Removed** and the behavioral notes under **Changed**.

### Added

- Single `hluk` CLI with subcommands `run`, `snapshot save` / `snapshot run`, and `bench` (`cold` / `cold-snap` / `warm-restore` / `warm-stateful` / `parallel`). Flags: `--mount HOST:GUEST[:ro]`, `--net` / `--net-allow` / `--net-block` / `--port`, `--exec`, `--guest-exec` (urunc-style, runs a binary baked into the initrd), `--entry`, `--env KEY=VALUE`, and `--scratch-mb`.
- Library API: a `SandboxBuilder` — `from_initrd(rootfs)` / `from_kernel` / `from_snapshot`, then `.boot()` to get a running sandbox — plus the `run` dispatch call, `Mount`, `Exec`, `GuestConfig`, and re-exported `Snapshot` / `OciTag`. `hluk` is built on the same API.
- 11 guest runtimes on a 3-tier support policy (`docs/guest-support-tiers.md`), a shared C driver toolkit, and a CPython conformance suite. `.NET` runs both ahead-of-time (AOT) and in-guest JIT (Roslyn source compilation).
- Typed `fs_*` / `net_*` host functions with new filesystem operations (`rename`, `symlink`, `readlink`, hard `link`, `chmod`), multi-mount support, `net_resolve` (host DNS), real guest stdin (`ReadStdin` + EOF), and host environment-variable passthrough (`--env`, re-applied across snapshot restore).
- `--kernel <path>` (advanced) to boot an external kernel instead of the embedded one, and a reproducible native-kernel test fixture (`just build-native-kernel` / `just verify-native-kernel`).
- Snapshot save/restore as OCI-layout directories; macOS (`hvf`) support; parallel multi-VM benchmarking; on-demand Windows surrogates.

### Changed

- **Guest-to-host boundary**: a single JSON-RPC `__dispatch` function plus a host-side `ToolRegistry` became many small, typed FlatBuffer host functions returning real `-errno` (Linux numbers, with a Win32/Winsock-to-Linux translation table).
- **Boot metadata**: pushed as magic-tagged TLVs prepended to the initrd became pulled via host functions at boot (`GetCmdLine`, `GetInitrdBase/Size`, `GetWallClockNs`, `GetEnvVars`, …), re-answerable after a snapshot restore.
- **Filesystem sandbox**: a hand-rolled path resolver became [`cap-std`](https://docs.rs/cap-std) with kernel-enforced `openat2(RESOLVE_BENEATH)` on Linux (component-by-component resolution on Windows). **Networking**: blocking `socket2` became non-blocking `rustix` with a `net_poll` readiness model.
- **Guest memory**: a no-paging design with a bespoke `lib/cpiovfs` and `lib/ukmmap` became the standard Unikraft paging/vmem/mmap stack with a ramfs initrd.
- **Kernel provisioning**: per-example `kraft` builds became one reproducible, Docker-built Unikraft kernel embedded in the binary via `include_bytes!` and verified in CI (kraftkit dropped).
- **VMM**: `hyperlight-host` 0.16 to 0.17. On Linux the default build is KVM-only (for the fast `MADV_DONTNEED` snapshot-restore path); MSHV support is behind `--features mshv`.
- **Behavioral (breaking)**: in 0.12.x `--port` implied `--net`; now `--port` requires an explicit `--net` (or `--net-allow` / `--net-block`) and errors on its own. Under `--net`, the default `AllowAll` policy permits the host loopback interface (needed for intra-guest server+client patterns); `--net-allow` / `--net-block` still block loopback.
- **PowerShell** runtime moved from a 7.6.x tarball to the 7.4 (LTS) Alpine image.
- The Unikraft kernel is now embedded by default (0.12.x took a positional kernel path); use `--kernel` to override it.

### Removed

- Wasm custom host tools (`--tool`, `--tool-wasi-*`), the public `ToolRegistry` / `SandboxBuilder::tool()` extension API, and the WASIp1 host-function sandbox.
- The `pyhl` Python tool (image pull from GHCR, warm-then-snapshot, `--deterministic`) and the `multifn-test` / `pydriver-run` dev binaries; the snapshot workflow folded into `hluk snapshot`.
- The `--memory` / `--stack` knobs (replaced by `--scratch-mb`), the reserved-mountpoint rejection list (`/`, `/bin`, `/dev`, `/proc`, `/sys`, `/usr`), and the implicit default `/host` mount path (mounts now require an explicit guest path).
- Kernel-internal: the bespoke `lib/cpiovfs`, the `/dev/hcall` userspace device, the per-syscall TSC profiler, and the trace ports. File-backed `mmap` and demand paging move from the custom `lib/ukmmap`/`cow.c` to the standard `ukvmem` fault handler. (`mmap`'s `mremap` is currently `ENOSYS`; glibc tolerates it.)
- The `app-elfloader` and `kraftkit` forks; the platform builds against upstream `app-elfloader` and a single `unikraft` kernel fork.
- Docs: the old `host_functions.md` (dispatch wire format / attack surface) and `python-packages.md`.

### Fixed

- Host-mount path-escape resolution is now OS-enforced (`openat2` `RESOLVE_BENEATH` / `RESOLVE_NO_MAGICLINKS` on Linux; component-by-component on Windows), with defense-in-depth `:ro` enforcement on both the VFS and host sides.
- Guest output is captured via a `HostPrint` host function (one VM exit per buffer instead of per byte) and exposed programmatically through `GuestConfig::drain_output`.
